# Council Init — tailor the council to this project

Runs once per project. It removes the manual persona-surgery step: instead of copying a council and
hand-editing experts, you point it at a repo and it generates the fit. Use the **`context-core`**
map discipline — **map the repo, do not deep-read it.**

**Read `references/roster/expert-catalog.md`** — it is the source of seats, their "applies when"
rules, and recast rules.

## Phase A — Detect stack & domain (map, don't ingest)

Glob/Grep for signals only:
- Language/build: `package.json`, `pyproject.toml`/`requirements.txt`, `go.mod`, `Cargo.toml`, `tsconfig.json`.
- Surfaces: a frontend dir / JSX-TSX? a server/API? a relational DB or migrations? an LLM/prompt
  pipeline? a numerical/data engine (pandas/numpy/parquet)? a CLI?
- Test + lint + build commands: scan `package.json` scripts, `pytest.ini`/`pyproject`, CI files,
  `Makefile`, `*.bat`/`*.ps1`.

Cap the read at config/skeleton files. You are classifying, not reviewing.

## Phase B — Select & recast the roster

For each seat in the catalog, decide **include / drop / recast** by its "applies when" rule:
- **Include** if the surface exists. **Drop** if it doesn't (e.g. no frontend → drop Dodds/Saarinen/Friedman).
- **Recast** to fit the domain, keeping the reference doc and recording why. Encoded examples
  (from the catalog): non-Node backend → generic backend seat; non-Postgres store → data-integrity
  seat; no-LLM numeric engine → numerical seat reusing `quality-llm.md`; non-Vercel → general
  performance/pipeline seat.

Keep the named-expert device (project decision #3). Fowler and Beck are never dropped.

## Phase C — Detect the gates

Record the project's **real** commands as the mode gates (do NOT assume tsc/vitest/cypress):
- test (e.g. `pytest`, `npm test`, `go test ./...`),
- lint (e.g. `npm run lint`, `ruff`, `golangci-lint`),
- build/compile (e.g. `python -m py_compile`, `npm run build`, `tsc --noEmit`),
- any e2e. Mark which are MANDATORY vs recoverable.

## Phase D — Propose, then write the config

Present the tailored roster + gates to the user for confirmation (adjust on request). Then write
`<project-root>/.council/council.config.md`:

```
# Council config — <project name>
Generated by council-init on <date>. Re-run to re-tailor (merge + show diff).

## Stack context
<2–4 lines: languages, frameworks, stores, surfaces, deploy target, hard safety rules>

## Roster (seat → domain → reference doc)
- <Seat> (<domain>) → references/<file>.md   # <recast note, if any>
- …

## Gates
- grounding:  <commands>            # run at Core phase 1
- verification: <commands>          # run at Core phase 10 (must pass)
- mandatory: <which gate blocks the run if it can't run>

## Memory
- namespace: conventions.md
```

## Phase E — Seed memory

If `conventions.md` doesn't exist at the project root, create it with the standard header
(Accepted Patterns / Enforced Conventions sections, empty). If obvious accepted patterns surfaced
during detection, propose them (don't auto-write).

## Re-runs

On a later run, **merge** into the existing `council.config.md` and show a diff rather than
overwriting — the roster and gates may have been hand-tuned since.

## Output

Confirm to the user: the roster (with any recasts and why), the detected gates, and the config path.
`council-review` and future modes now read this config instead of the default roster.
